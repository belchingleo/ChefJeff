# Agent integration

Cocos provides rendering and player input; Python maintains authoritative kitchen state. The agent selects an action, and the engine validates and executes it.

A new agent does not have to be Jeff with another model: it can play through the environment interface directly, `observe()` and `act()` on an `AgentPort` ([env-v1](architecture/environment-api.md)); `example_agent.py` is a complete one, and `scripts/benchmark.py` runs either kind.

## Decision flow

`SpatialKitchen.snapshot()` and `actions('jeff')` → client `payload(state, actions)` → asynchronous `ask(payload)` → `DecisionLoop` validation → `kitchen.start()` → movement/work → completion event. Before a model is sent the request, `harness.for_model` leaves out its version tags (the `state` keys ending in `_version`, and `input_language`): they are bookkeeping, not facts about the kitchen. The round's record keeps the request with them, and research replay checks against that (since 2026-11-20).

Use actor IDs `human` and `jeff`. TypeSafe's provider ID `jev`, model IDs and `jev.py` adapter name remain unchanged. Old local memory actor fields are normalized when read; model identities and historical files remain intact.

Track requests, selections, accepted actions and `action_done` separately. A legal choice can become stale while the request is in flight.

## Compatible services

Choose a compatible Chat Completions service in Settings and supply your own HTTPS base URL, model and key. `CompatibleClient` sends structured state, rules and candidates. Return JSON such as:

```json
{"choice": "wash", "sprint": false}
```

`choice` must occur in the current `questions.next_action.criteria`; choose `wash` only when offered. `sprint` is a boolean when requested.

## New adapters

Jeff's input is assembled in `harness.py`: `harness.payload` builds the kitchen, rules and listed actions, and `harness.compose` adds recent events and decisions, player messages and memory. Follow `CompatibleClient` in `player_api.py`, which inherits `SpatialJevClient` from `whitebox_server.py`:

- `payload(state, actions)` returns the harness input, adding only the adapter's own fields (such as `model`), without modifying the game.
- `ask(payload)` returns a dictionary with `choice`, following existing `sprint`, `model`, `usage` and `latency` conventions.
- Add an explicit branch in `create_client(config, setting)`, with settings validation and UI choices.
- Use offline test doubles for invalid choices, stale replies, timeouts, budgets and recovery. Keep real keys out of CI.

Hosted play uses `BrowserRelay` plus `hosted/browser-agent.js`; add browser-provider support there separately. `BrowserRelay` only accepts a validated choice, sprint flag and numeric usage and never stores credentials. Jev's explicit opt-in path uses `hosted_jev.py` at `/api/model/jev`: it requires the authenticated page token, game/task ID and consent version, forwards only the server-created task (or a fixed connection test) to the fixed Jev URL/model, and keeps the supplied key local to HTTP request processing. Never send that body through game-command receipts/journals or add a user-selected forwarding URL.

## Jeff's plan (removed)

Two plan modes, the plan (`jeff_plan`, `plan-v2`) and the two-step rolling intent (`rolling_intent`, `rolling-v3`), asked Jeff for the work he intended next in `questions.plan_step_*` and `plan_keep`. Both went on 2026-11-20 with their code, Settings switches and the plan line: off since option-links-v3, and asking ahead replaced what the two-step intent was for. Records from before keep `conditions.jeff_plan` and `payload.jeff_plan`; their requests are not rebuilt request by request. The browser now sends the only extra answer, `put_where`, under `answers`.

One-press options are released (`one_press.py`, version `one-press-v6`: v4 added put then fetch, v6 adds a free stove to the put places (the engine's own `put pot <stove>`, listed while Jeff holds a pan or pot; before it he could set an empty pan down only on a counter, a supply or the floor after plating, about 3.5 times a round in the user's 2026-11-21 level-4 rounds and never straight back on a stove), v5 words `put then take` of a pan or pot on a stove as the engine's own lift, "then lift the frying pan from Stove 1 (stops heating off the stove; occupies your hands)", where v4 said "then take <its food> from Stove 1"): `features.json` has `one_press` on, the page has no switch for it, and turning it off there (then restarting) is the rollback. (Until then they were two trial switches, `put_then_take` and `wash_from_returns`, set with `POST /api/one-press`, which is gone.) With it on, `next_action` can also offer `put then take <station>` (Jeff holds an item, another lies on a station he could take with empty hands, and no other listed action, walks and throws aside, is at that station; the plain `go <station>` then drops out as for any other action there), under the same switch `put then chop <board>` and `put then wash <sink>` (the same, for chopping what lies on a board or washing the dirty plate in the sink, which the engine lists only with empty hands; their labels give the seconds of work left, as the engine's own chop and wash labels do; `one-press-v1` had neither, and `one-press-v2` gave no seconds) and `wash from <plate return>` (a dirty plate is on the plate return and the sink is empty, not burning and not taken by the other chef). Whenever such an option is listed and Jeff holds something, the request also has `questions.put_where`, a `choice` question whose criteria are the put places already in `next_action` (`put …`, `drop` and, since v6, `put pot <stove>`; same keys and labels); it is used only when `next_action` is one of these options. `state.rules.one_press` (`one_press.RULE`) and `state.one_press_version` say so. Answer `put_where` like the plan questions: decision models as a `choice` question, chat models as a `"put_where": "<key>"` field (`harness.PUT_WHERE_CHAT_RULE`), the browser relay inside `plan`; `harness.choice_answer` reads it, and a missing or unlisted answer falls back to the first listed put place (logged as `fallback`). The loop then runs the steps as ordinary starts: each is checked when it comes, a step that cannot be done ends the chain (`one_press_end`, reason `step_not_possible`), and another applied choice replaces it (`replaced`); a change of urgency asks even while a step is under way. A `continue` reply to a request made during a chain holds as long as that same chain is still under way (logged `chain_continue`), though the chain has moved on to its next step: such replies used to be dropped as stale and Jeff asked again (about 5 a round in the user's 2026-11-21 rounds, all during multi-step one-press options), with the next request held up meanwhile.

## Feature switches (`features.json`)

Jeff's harness features, the ones that change what he is asked or how his answers are carried out, are switched in one file, `features.json`, checked by `features.py` when the server starts (a wrong name, stage, value or version stops it). Each has a `stage`: `release` is on unless the file says `"on": false`, with no switch in the page, so turning it off and restarting rolls it back; `trial` is off unless the file says `"on": true`. The page offers no switch for any feature (the last one, 步骤提示 for `option_links`, went on 2026-11-20; `option_links` is now released, and `off_for` sets it per model service). `version` must be the version the code implements: the file only turns features on and off, and going back to an older version still means going back in the code. Today `one_press` is released, so every round runs with it. ## Shared rules and extension points

Human input is continuous movement plus nearby actions; agent input is higher-level action selection. Both share movement speed, contact, access sides, preparation times and item constraints. Working chefs cannot be pushed away; pans and pots heat only while on a stove.

Maps are validated by `map_definition.py`. Recipe legality and some processing conditions remain in Python; the roadmap moves them into validated data before introducing map and recipe editors. Visual ingredient layers are independent from legality.

Future benchmark work will define a complete-session scenario schema, partner/configuration conditions and comparison methods with the community. Record input language and build identity alongside results; receipt of a message or memory is observable, while understanding or causal adaptation requires an appropriate comparison.

# Agent 接入

Cocos 提供画面与玩家输入，Python 维护权威厨房状态。Agent 选择动作，由引擎校验并执行。

新的 agent 不一定是"换个模型的 Jeff"：也可以直接通过环境接口来玩，即 `AgentPort` 上的 `observe()` 和 `act()`（[env-v1](architecture/environment-api.md)）。`example_agent.py` 是一个完整的例子，`scripts/benchmark.py` 两种 agent 都能跑。

## 决策链路

`SpatialKitchen.snapshot()` 与 `actions('jeff')` → client `payload(state, actions)` → 异步 `ask(payload)` → `DecisionLoop` 校验 → `kitchen.start()` → 移动／加工 → 完成事件。发给模型之前，`harness.for_model` 去掉请求里的版本标记（`state` 里以 `_version` 结尾的各项和 `input_language`）：它们只供记录核对，不是厨房里的事实。本局记录保留带标记的完整请求，研究重放照旧按它核对（2026-11-20 起）。

角色 ID 使用 `human` 和 `jeff`。TypeSafe 的 provider ID `jev`、模型名及 `jev.py` 适配器名称保留。旧本地记忆读取时转换角色字段，模型身份与历史文件保持原样。

分别记录请求、选择、动作接受和 `action_done`；请求在途时，原本合法的选择也可能过期。

## 兼容服务

在设置中选择兼容 Chat Completions 服务，填写自己的 HTTPS Base URL、模型与 Key。`CompatibleClient` 发送结构化状态、规则与候选动作，返回 JSON，例如：

```json
{"choice": "wash", "sprint": false}
```

`choice` 必须位于当前 `questions.next_action.criteria`；只有提供 `wash` 候选时才能选择它。请求包含冲刺问题时，`sprint` 为布尔值。

## 新增适配器

Jeff 的输入在 `harness.py` 中拼装：`harness.payload` 生成厨房状态、规则说明和可选动作，`harness.compose` 再加入最近事件与选择、玩家消息和记忆。参考 `player_api.py` 中的 `CompatibleClient`，它继承 `whitebox_server.py` 的 `SpatialJevClient`：

- `payload(state, actions)` 返回 harness 生成的输入，只添加适配器自己的字段（如 `model`），不改变游戏。
- `ask(payload)` 返回含 `choice` 的字典，遵循现有 `sprint`、`model`、`usage`、`latency` 字段约定。
- 在 `create_client(config, setting)` 增加明确分支，同步设置校验与界面选项。
- 用离线替身覆盖非法选择、过期回复、超时、额度和恢复，CI 不使用真实密钥。

托管版使用 `BrowserRelay` 与 `hosted/browser-agent.js`，需要另外接入浏览器供应商适配。中继仅接收校验后的动作、冲刺值和数值用量，不接收供应商凭据。

fetched) down onto Board 1”，后面写走几秒，有联动表时还写另一位厨师接着能做什么）。引擎接受这一步走路，虽然平时不给 Jeff 列出（`throw_spot_walk`）；不先放下东西，所以没有 `put_where`；到了那格扔出去如果已经落不到那里，这个动作就结束。另有三个没有玩家开关的试验（`work_notes.py`，默认关），在选项上写明它通向什么活，来自 2026-11-21 对第 5 关来回倒腾的诊断（Jev 几乎总选概率最高的选项，厨房不变时就重复；开着请求的各块时 Jeff 的菜板堵住，能推进工作的选项后面没有一句话，放下和拿回反而有）：`own_chain`（`own-chain-v1`）给做完后 Jeff 手里会拿着东西的选项写上他自己接着最短几步（最多两步）能走到的活，或者交给另一位厨师后对方能干的活（“then you could: Put the held beef (chopped) on Counter 4; then the other chef could: Take ..., then Put beef (chopped) into the frying pan on Stove 1”），只有一步活时不写，因为联动表已经写了；`plate_result`（`plate-result-v1`）让装盘和组装的选项写明盘子会变成什么、哪张等待中的订单要它（“makes a Steak; order O4 waits for a Steak, 29.9 s left”）；`board_taken`（`board-taken-v1`）把不在菜板上切的东西放到菜板上时，写明这块菜板就被占了、还有几样够得着的食材等着切，`next_action` 和 `put_where` 里都写。每局的开局记录和研究记录都带上当时的开关（`features`：每个功能的 `on` 和 `version`）。游戏规则、关卡、玩家偏好和请求间隔这类数值仍在各自的文件里（`ai_ask_on_step_end` 暂时留在 `config.json`，因为搬走会改变每局的配置指纹）。

## 共用规则与扩展点

人类持续移动并执行就近动作，agent 选择较高层动作。双方共用移动速度、碰撞、操作侧、加工时间与物品约束。工作中的厨师不会被推离；锅仅在灶台上加热。

地图由 `map_definition.py` 校验。菜谱合法性与部分加工条件仍在 Python 中，路线图是先转为可校验数据，再接地图与菜谱编辑器。视觉配料叠层独立于合法性判断。

未来与社区共同定义完整对局 scenario schema、搭档／配置条件及对照方法。结果需记录输入语言和构建标识；消息或记忆送达可以直接观察，理解与因果适应需要相应对照。
