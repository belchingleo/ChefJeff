# Agent integration

Cocos provides rendering and player input; Python maintains authoritative kitchen state. The agent selects an action, and the engine validates and executes it.

A new agent does not have to be Jeff with another model: it can play through the environment interface directly, `observe()` and `act()` on an `AgentPort` ([env-v1](architecture/environment-api.md)); `example_agent.py` is a complete one, and `scripts/benchmark.py` runs either kind.

## Decision flow

`SpatialKitchen.snapshot()` and `actions('jeff')` → client `payload(state, actions)` → asynchronous `ask(payload)` → `DecisionLoop` validation → `kitchen.start()` → movement/work → completion event.

Use actor IDs `human` and `jeff`. TypeSafe's provider ID `jev`, model IDs and `jev.py` adapter name remain unchanged. Old local memory actor fields are normalized when read; model identities and historical files remain intact.

Track requests, selections, accepted actions and `action_done` separately. A legal choice can become stale while the request is in flight.

## Compatible services

Choose a compatible Chat Completions service in Settings and supply your own HTTPS base URL, model and key. `CompatibleClient` sends structured state, rules and candidates. Return JSON such as:

```json
{"choice": "wash", "sprint": false}
```

`choice` must occur in the current `questions.next_action.criteria`; choose `wash` only when offered. `sprint` is a boolean when requested.

## New adapters

Jeff's input is assembled in `harness.py`: `harness.payload` builds the kitchen, rules and listed actions, and `harness.compose` adds recent events and decisions, player messages and memory. Follow `CompatibleClient` in `player_api.py`, which inherits `SpatialJevClient` from `whitebox_server.py`:

- `payload(state, actions)` returns the harness input, adding only the adapter's own fields (such as `model`), without modifying the game.
- `ask(payload)` returns a dictionary with `choice`, following existing `sprint`, `model`, `usage` and `latency` conventions.
- Add an explicit branch in `create_client(config, setting)`, with settings validation and UI choices.
- Use offline test doubles for invalid choices, stale replies, timeouts, budgets and recovery. Keep real keys out of CI.

Hosted play uses `BrowserRelay` plus `hosted/browser-agent.js`; add browser-provider support there separately. `BrowserRelay` only accepts a validated choice, sprint flag and numeric usage and never stores credentials. Jev's explicit opt-in path uses `hosted_jev.py` at `/api/model/jev`: it requires the authenticated page token, game/task ID and consent version, forwards only the server-created task (or a fixed connection test) to the fixed Jev URL/model, and keeps the supplied key local to HTTP request processing. Never send that body through game-command receipts/journals or add a user-selected forwarding URL.

## Jeff's plan (plan questions)

With the plan switch on, a request made while no plan holds also carries `questions.plan_step_1` to `plan_step_4`: `choice` questions whose criteria are the level's work items (`harness.work_items`: fetch, chop, cook or plate an ingredient, take a clean plate, serve, collect or wash plates), with `none` from step 2 on to end the plan there. While a plan holds, the request shows it as `state.jeff_plan` (its steps, each marked done) and asks `questions.plan_keep` (`keep` or `drop`) instead. The adapter returns each chosen key next to the action: a chat model writes `"plan_step_1": "<key>"` and so on in the same JSON (its system prompt gets `harness.PLAN_CHAT_RULE` only when plan questions are asked), a decision model answers each as a choice under `answers`. Pass the answers through `harness.plan_answer(answers, payload)`, which returns `{}` when nothing was asked, `{"plan": {"steps": [...]}}` (stopping at `none` or a key that was not offered) or `{"plan": {"keep": True, False or None}}`. `DecisionLoop` takes the plan only from a fresh reply and a bad plan answer never rejects the action. It ticks a step when Jeff finishes an action doing that work (`harness.work_item`), in any order; the plan has no clock and ends when every step is done, when Jeff answers `drop`, or when the human sends a new preference, and the next request, sent at once like after a finished step, asks for a new one. Hosted play does the same in `hosted/browser-agent.js`, which sends the answers as `plan` with the result.

The two-step rolling intent is a trial plan mode (`mode` `rolling`, rules version `rolling-v3`, off by default). Every request asks `questions.plan_step_1` (a note on `next_action`: the work item the chosen action does or is for) and `plan_step_2` (the one after it, or `none`), with the same work-item criteria, and never `plan_keep`. The newest valid answer is shown as history, not as a plan: as `intent` on the decision it was noted with in `state.recent_decisions`, ticked as above, under `state.rules.intent` = `harness.ROLLING_RULE`; there is no `state.jeff_plan`. A new valid answer replaces it and a missing one leaves it. While food in a pan on a stove is within `harness.ROLLING_YIELD_SECONDS` (8) game seconds of burning, the intent is left out of the request (the two questions are still asked) and shows again once no pan is that close. (`rolling-v1` showed it as `state.jeff_plan` and `rolling-v2` as history without that exception; with a pan about to burn, an intent shown either way kept Jeff on it.) The answers are read exactly as above (`harness.plan_answer`), so clients need no change. With `ai_ask_on_step_end` on, a change in an order's or a pan's countdown band asks even while Jeff's step will end before a reply could return (the four-step plan and plan mode off still wait for the step to end).

One-press options are released (`one_press.py`, version `one-press-v5`: v4 added put then fetch, v5 words `put then take` of a pan or pot on a stove as the engine's own lift, "then lift the frying pan from Stove 1 (stops heating off the stove; occupies your hands)", where v4 said "then take <its food> from Stove 1"): `features.json` has `one_press` on, the page has no switch for it, and turning it off there (then restarting) is the rollback. (Until then they were two trial switches, `put_then_take` and `wash_from_returns`, set with `POST /api/one-press`, which is gone.) With it on, `next_action` can also offer `put then take <station>` (Jeff holds an item, another lies on a station he could take with empty hands, and no other listed action, walks and throws aside, is at that station; the plain `go <station>` then drops out as for any other action there), under the same switch `put then chop <board>` and `put then wash <sink>` (the same, for chopping what lies on a board or washing the dirty plate in the sink, which the engine lists only with empty hands; their labels give the seconds of work left, as the engine's own chop and wash labels do; `one-press-v1` had neither, and `one-press-v2` gave no seconds) and `wash from <plate return>` (a dirty plate is on the plate return and the sink is empty, not burning and not taken by the other chef). Whenever such an option is listed and Jeff holds something, the request also has `questions.put_where`, a `choice` question whose criteria are the put places already in `next_action` (`put …` and `drop`, same keys and labels); it is used only when `next_action` is one of these options. `state.rules.one_press` (`one_press.RULE`) and `state.one_press_version` say so. Answer `put_where` like the plan questions: decision models as a `choice` question, chat models as a `"put_where": "<key>"` field (`harness.PUT_WHERE_CHAT_RULE`), the browser relay inside `plan`; `harness.choice_answer` reads it, and a missing or unlisted answer falls back to the first listed put place (logged as `fallback`). The loop then runs the steps as ordinary starts: each is checked when it comes, a step that cannot be done ends the chain (`one_press_end`, reason `step_not_possible`), and another applied choice replaces it (`replaced`); a change of urgency asks even while a step is under way.

## Feature switches (`features.json`)

Jeff's harness features, the ones that change what he is asked or how his answers are carried out, are switched in one file, `features.json`, checked by `features.py` when the server starts (a wrong name, stage, value or version stops it). Each has a `stage`: `release` is on unless the file says `"on": false`, with no switch in the page, so turning it off and restarting rolls it back; `trial` is off unless the file says `"on": true`, and with `"player_switch": true` it shows in Settings → AI teammate as a (测试) switch whose default is `on`. `version` must be the version the code implements: the file only turns features on and off, and going back to an older version still means going back in the code. Today `one_press` and the two-step intent `rolling_intent` (`rolling`) are released, so every round runs with them, and the other plan mode, `jeff_plan` (`choice`), is a trial without a player switch, off; one plan mode at a time. `communication.jeff_plan.available` lists the modes the page offers, none today, so Settings shows no plan switch. A server can change the switches without a new release: `/etc/chefjeff/features.override.json` (or the path in `CHEFJEFF_FEATURES_OVERRIDE`) may set `on`, `player_switch` and `off_for` of the release's features, is checked like the file, and is written with `python3 features.py set|unset|show|check`; each round takes the switches as it starts, and a feature set this way is recorded with `"source": "server"` (docs/hosted-deployment.md). A feature that is on may list, in `off_for`, model services (ids in `model-providers.json`) whose rounds start with it off (`features.model_defaults`, recorded with `"source": "model"`): the local game takes the service from the saved connection, the hosted page reports only the preset id with `/api/browser-ready`, and a free model is the site's own. `features.json` names none; the local play set's override gives `option_links_partner` and `split_floor` to every service but Perplexity, which passes food across the split floor without them. `undo_note` is a trial without a player switch (version `undo-note-v2`, off in `features.json` since 0.9.0-beta.1): with it on, an option that would take back what Jeff's last step put down, or put back what it took, carries a factual note with the time (`undo_note.py`; the player sees no note), and each request's research record keeps that step so it can be rebuilt; `scripts/undo_note_check.py` re-asks logged moments with and without the notes. v2: requests asked ahead carry the notes too, for the step under way, which is Jeff's last step at the moment they describe (v1 kept ask_ahead from asking while it was on). v3: lifting a pan or pot from a stove is a take and putting one on a stove a put, so returning a lifted pan straight to its stove is noted as putting it back. `ask_ahead` is a trial without a player switch (version `ask-ahead-v2`, `ask_ahead.py`): at the moment today's loop decides not to ask because Jeff's step would end before a reply could come (`outlasts_reply`), it plays a fork of the kitchen (`Kitchen.fork`: no record hooks, its own route caches, inputs and random state) forward to the end of that step, with the other chef keeping what it does, and asks with that state, in the same format as any request. The answer is held until the step ends and carried out only if the step ended with `action_done`, Jeff holds what the prediction says, the countdown bands at the step's end match the predicted ones, the chosen action is still listed and the answer is not older than `ai_max_response_age`; otherwise it is dropped and Jeff is asked at once as before. ## Shared rules and extension points

Human input is continuous movement plus nearby actions; agent input is higher-level action selection. Both share movement speed, contact, access sides, preparation times and item constraints. Working chefs cannot be pushed away; pans and pots heat only while on a stove.

Maps are validated by `map_definition.py`. Recipe legality and some processing conditions remain in Python; the roadmap moves them into validated data before introducing map and recipe editors. Visual ingredient layers are independent from legality.

Future benchmark work will define a complete-session scenario schema, partner/configuration conditions and comparison methods with the community. Record input language and build identity alongside results; receipt of a message or memory is observable, while understanding or causal adaptation requires an appropriate comparison.

# Agent 接入

Cocos 提供画面与玩家输入，Python 维护权威厨房状态。Agent 选择动作，由引擎校验并执行。

新的 agent 不一定是"换个模型的 Jeff"：也可以直接通过环境接口来玩，即 `AgentPort` 上的 `observe()` 和 `act()`（[env-v1](architecture/environment-api.md)）。`example_agent.py` 是一个完整的例子，`scripts/benchmark.py` 两种 agent 都能跑。

## 决策链路

`SpatialKitchen.snapshot()` 与 `actions('jeff')` → client `payload(state, actions)` → 异步 `ask(payload)` → `DecisionLoop` 校验 → `kitchen.start()` → 移动／加工 → 完成事件。

角色 ID 使用 `human` 和 `jeff`。TypeSafe 的 provider ID `jev`、模型名及 `jev.py` 适配器名称保留。旧本地记忆读取时转换角色字段，模型身份与历史文件保持原样。

分别记录请求、选择、动作接受和 `action_done`；请求在途时，原本合法的选择也可能过期。

## 兼容服务

在设置中选择兼容 Chat Completions 服务，填写自己的 HTTPS Base URL、模型与 Key。`CompatibleClient` 发送结构化状态、规则与候选动作，返回 JSON，例如：

```json
{"choice": "wash", "sprint": false}
```

`choice` 必须位于当前 `questions.next_action.criteria`；只有提供 `wash` 候选时才能选择它。请求包含冲刺问题时，`sprint` 为布尔值。

## 新增适配器

Jeff 的输入在 `harness.py` 中拼装：`harness.payload` 生成厨房状态、规则说明和可选动作，`harness.compose` 再加入最近事件与选择、玩家消息和记忆。参考 `player_api.py` 中的 `CompatibleClient`，它继承 `whitebox_server.py` 的 `SpatialJevClient`：

- `payload(state, actions)` 返回 harness 生成的输入，只添加适配器自己的字段（如 `model`），不改变游戏。
- `ask(payload)` 返回含 `choice` 的字典，遵循现有 `sprint`、`model`、`usage`、`latency` 字段约定。
- 在 `create_client(config, setting)` 增加明确分支，同步设置校验与界面选项。
- 用离线替身覆盖非法选择、过期回复、超时、额度和恢复，CI 不使用真实密钥。

托管版使用 `BrowserRelay` 与 `hosted/browser-agent.js`，需要另外接入浏览器供应商适配。中继仅接收校验后的动作、冲刺值和数值用量，不接收供应商凭据。

## Jeff 的计划（计划题）

计划开关打开后，在没有计划时发出的请求会多出 `questions.plan_step_1` 到 `plan_step_4`，类型为 `choice`，选项是本关的工序（`harness.work_items`：取、切、下锅、装盘某种食材，拿干净盘子，出餐，收脏盘，洗盘子），从第 2 步起多一个 `none`，表示计划到此为止。有计划时，请求在 `state.jeff_plan` 里给出这份计划（每一步是否已做完），并改问 `questions.plan_keep`（`keep` 或 `drop`）。适配器把选中的键和动作一起返回：对话模型在同一个 JSON 里写 `"plan_step_1": "<键>"` 等字段（只有问到计划题时，系统提示才加上 `harness.PLAN_CHAT_RULE`），决策模型在 `answers` 里逐题以选择题形式回答。把这些回答交给 `harness.plan_answer(answers, payload)`：没有问到时返回 `{}`，问步骤时返回 `{"plan": {"steps": [...]}}`（遇到 `none` 或不在选项里的键就停），问去留时返回 `{"plan": {"keep": True、False 或 None}}`。`DecisionLoop` 只采用未过期回复里的计划，计划回答有误也不会拒绝动作。Jeff 每做完一个对应工序的动作（`harness.work_item`），计划里那一步就打勾，不要求顺序。计划没有时限，全部做完、Jeff 回答 `drop`，或玩家发来新的偏好时结束，下一次请求会像一步做完时那样马上发出，问新的计划。托管版在 `hosted/browser-agent.js` 里做同样的处理，回答随结果放在 `plan` 里发回。

两步打算是一种试验中的计划模式（`mode` 为 `rolling`，规则版本 `rolling-v3`，默认关闭）。每次请求都问 `questions.plan_step_1`（对 `next_action` 的备注：选的动作所做的、或为之去做的那道工序）和 `plan_step_2`（之后打算做的下一道，或 `none`），选项同样是本关的工序，从不问 `plan_keep`。最新的有效回答当作历史记录给出，而不是计划：附在 `state.recent_decisions` 里记下它的那条决定上，字段名 `intent`，按上面的方式打勾，规则说明是 `state.rules.intent` = `harness.ROLLING_RULE`，不再有 `state.jeff_plan`。新的有效回答替换旧的，没有回答就保留旧的。灶上锅里的食物离糊不到 `harness.ROLLING_YIELD_SECONDS`（8）个游戏秒时，这次请求不给出打算（两道题照常问），等没有锅这么接近糊了再给出。（`rolling-v1` 放在 `state.jeff_plan`，`rolling-v2` 当作历史记录但没有这条例外；锅快糊时，只要给他看打算，他都会照着做。）回答的读取方式和上面完全相同（`harness.plan_answer`），客户端不用改。`ai_ask_on_step_end` 打开时，订单或锅的倒计时跨档，即使 Jeff 这一步会在回复到达前结束，也会马上问（四步计划和关闭计划时仍等这一步做完）。

一键操作已经正式上线（`one_press.py`，版本 `one-press-v5`：v4 加了「先放下再取」，v5 把从灶台拿锅的 `put then take` 写成引擎自己的端锅说明「再端起灶台 1的平底锅（离开灶台停止加热，占手持位）」，v4 写的是「再从灶台 1拿起<锅里的食物>」）：`features.json` 里 `one_press` 是打开的，页面上没有它的开关，要回退就在那里关掉再重启。（此前是两个试验开关 `put_then_take` 和 `wash_from_returns`，用 `POST /api/one-press` 设置，这个接口已经去掉。）打开时，`next_action` 里可能多出 `put then take <工位>`（Jeff 手里拿着东西，另一个工位上放着他空手就能拿的东西，而且除了走路和抛掷，没有别的选项在那个工位上；这时那个工位的 `go <工位>` 会像有别的动作在那里时一样去掉），同一个开关下还有 `put then chop <菜板>` 和 `put then wash <水槽>`（条件相同，换成切菜板上的食材、洗水槽里的脏盘子，引擎只在空手时列出这两种动作；说明里写着还要切或洗几秒，和引擎自己的切、洗说明一样；`one-press-v1` 没有这两种，`one-press-v2` 没写秒数），以及 `wash from <回收口>`（回收口上有脏盘子，水槽空着、没着火、也没被另一位厨师占着）。只要列出了这类选项而 Jeff 手里拿着东西，请求就多一道 `questions.put_where`，类型为 `choice`，选项就是 `next_action` 里已有的放置选项（`put …` 和 `drop`，键和说明都相同），只在 `next_action` 选了这类选项时才用。`state.rules.one_press`（`one_press.RULE`）和 `state.one_press_version` 说明这一点。`put_where` 的回答方式和计划问题相同：决策模型当作一道 `choice` 题，对话模型在 JSON 里加 `"put_where": "<键>"`（`harness.PUT_WHERE_CHAT_RULE`），浏览器中转放在 `plan` 里；由 `harness.choice_answer` 读取，没有回答或回答不在选项里时，用第一个列出的放置位置（记为 `fallback`）。之后决策循环把这几步当作普通动作依次开始：每一步轮到时再检查，做不了就结束整串（`one_press_end`，原因 `step_not_possible`），他另选并执行了别的动作就替换它（`replaced`）；进行中倒计时跨档也会马上问他。

## 功能开关（`features.json`）

会改变 Jeff 被问什么、或他的回答怎么执行的功能，都在一个文件 `features.json` 里开关，服务启动时由 `features.py` 检查（名字、阶段、取值或版本写错，服务就不启动）。每个功能有一个阶段 `stage`：`release`（已上线）默认打开，除非文件里写 `"on": false`，页面上没有它的开关，所以关掉再重启就是回退；`trial`（测试中）默认关闭，除非写 `"on": true`，写了 `"player_switch": true` 的会在「设置 → AI 搭档」里显示成（测试）开关，`on` 是它的默认值。`version` 必须是代码实现的版本：这个文件只管开关，要退回旧版本仍然要回退代码。目前 `one_press` 和两步打算 `rolling_intent`（`rolling`）已上线，每局都用；另一种计划模式 `jeff_plan`（`choice`）在测试中，没有玩家开关，默认关闭。计划模式一次只能开一种。`communication.jeff_plan.available` 列出页面提供哪几种，现在一种也没有，所以设置里不显示计划开关。服务器不用发新版本也能改开关：`/etc/chefjeff/features.override.json`（或 `CHEFJEFF_FEATURES_OVERRIDE` 指定的路径）可以改发布包里各功能的 `on`、`player_switch` 和 `off_for`，检查规则和开关文件一样，用 `python3 features.py set|unset|show|check` 写入；每局开局时读取当时的开关，用这种方式设置的功能在记录里标为 `"source": "server"`（见 docs/hosted-deployment.md）。打开的功能可以在 `off_for` 里列出一些模型服务（`model-providers.json` 里的编号），连这些服务时每局开局默认关闭它（`features.model_defaults`，记录里标为 `"source": "model"`）：本地游戏从保存的连接读服务，在线版页面通过 `/api/browser-ready` 只报告预设服务的编号，免费模型就是网站自己的服务。`features.json` 里没有写任何服务；本地试玩用的覆盖设置让 `option_links_partner` 和 `split_floor` 对 Perplexity 以外的服务都打开，因为 Perplexity 不靠它们也会隔着柜台传东西。`undo_note` 也在测试中，页面上没有它的开关（版本 `undo-note-v2`，从 0.9.0-beta.1 起在 `features.json` 里默认关闭）：打开后，如果某个选项正好会把 Jeff 上一步放下的东西拿回来，或者把他上一步拿起的东西放回原处，这个选项后面会附一句带时间的事实说明（`undo_note.py`，玩家看不到）；每次请求的研究记录会存下这一步，以便原样重建。`scripts/undo_note_check.py` 拿记录里的时刻，加说明和不加说明各问一遍模型做对比。v2：提前问的请求里也带这些说明，针对的是正在做的这一步，在请求描述的那一刻它就是 Jeff 的上一步（v1 开着它时不提前问）。v3：从灶台端起锅算“拿起”，把锅放上灶台算“放下”，所以刚端起的锅直接放回原灶台，会标为“放回原处”。`ask_ahead` 也在测试中，页面上没有它的开关（版本 `ask-ahead-v2`，`ask_ahead.py`）：在今天的决策循环因为“回复到达前这一步就会结束”（`outlasts_reply`）而决定不问的那一刻，它把厨房的一个副本（`Kitchen.fork`：不带记录钩子，路线缓存、引擎输入和随机状态都是自己的）推演到这一步结束，另一位厨师照旧做手上的事，再按那时的状态提问，格式和普通请求完全一样。回复要等这一步结束才处理，并且只有在以下条件都满足时才执行：这一步以 `action_done` 结束，Jeff 手里拿的和预测一致，这一步结束时的倒计时档位和预测一致，选中的动作仍在选项里，回复没有超过 `ai_max_response_age`；否则作废，马上按原来的方式重问。开着计划模式时不提前问，一键操作还有后续步骤时也不提前问。从 `ask-ahead-v2` 起（2026-11-19；此前是单独的试验开关 `ahead_throw`，`ahead-throw-v1`）：提前问到的“扔给队友”瞄准的是提问时对方所在的位置和格子，所以 Jeff 这一步结束前对方只要挪动，这个回复就会因“不在选项里”而作废；现在只要 Jeff 手里还是同一件东西、也还能扔给对方，就照常执行，朝对方现在的位置扔。Jeff 被问的内容不变。`reach_note` 也在测试中，页面上没有它的开关（版本 `reach-v1`，`reach_note.py`）：地面被柜台隔开时（第四关），请求里多一条规则 `rules.reach`，按引擎的判断（`SpatialKitchen.reaches`）列出哪些工位只有 Jeff 能到、哪些只有人类能到、哪些两边都能到；只写事实，不提传菜，也不提分工。地面连成一片时什么都不加。研究回放从记录的 `conditions.features` 读这个开关。`clear_text` 也在测试中，页面上没有它的开关，`features.json` 里默认打开（版本 `clear-text-v1`）：它把 `food_names`、`clear_names`、`engine_english`、`plate_names` 四部分一起打开，这四个在 2026-11-19 之前各是一个开关；研究回放两种写法都认。其中 `food_names`（版本 `names-v1`，`food_names.py`，2026-11-09 起默认打开）：关闭时 Jeff 读到的食物名字，是页面显示用的名字翻译过来的；牛肉的那组名字写于它还是唯一食材的时候，所以生牛肉叫 "Raw meat"，切好的叫 "Chopped"，熟的叫 "Cooked"，而菜谱和盘子的 `missing` 写的是 "beef (cooked)"；冰箱的取货动作写的是 "raw meat"，也没有任何工位说明自己出什么食材。打开后，散放的食材一律写成 `<食材> (<状态>)`，状态用菜谱里的词（as fetched、chopped、cooking、cooked、burnt）；盘子在这一局的订单会点这道菜时写菜名，否则写 "plate with" 加盘里的配料；锅写种类和里面的东西。所有提到食物的动作文字都用同一个名字（`Fetch beef (as fetched)`、`Take beef (cooked) from Counter 2`），每个食材箱用 `supplies` 写明出什么食材，`rules.food_names` 说明命名方式。名字由食材编号和状态拼出来，所以玩家关卡能用的每种食材都按同一规则命名（`tests/test_food_names.py` 把 12 种食材的每个状态都摆一遍）。生成请求时引擎处于命名模式（用的是上下文变量：厨房里什么都不改，只读视图仍然只读），所以页面、引擎事件和记录里的引擎输入都和以前一样；开关关闭时请求逐字节不变。`scripts/food_names_check.py`（`reask.py food_names`）用会话包重放记录里的对局，挑出 Jeff 空着手等待、而菜单需要的某种食材厨房里一份都没有的时刻，原样问一次、按开关打开后的样子再问一次。其中 `plate_names`（版本 `plate-names-v1`，`plate_names.py`）：选项或厨师当前任务里按位置提到的盘子、或厨师手里的盘子，都按请求里状态的叫法写明盘里有什么（“Fill the plate with bread on Counter 2 from your frying pan”“Put the held bread (as fetched) onto the clean plate at Counter 4”“Plate food from Stove 2 onto the held plate with bread”）；不说会做成什么菜、算给哪张订单，选项联动表里的行不改。研究回放从记录的 `conditions.features` 读这个开关。`option_effects` 是没有页面开关的试验（版本 `option-effects-v1`，`option_effects.py`，默认关闭）：next_action 里每个选项，如果做完这一步会直接带来结果，就在选项文字后面加一句 " (Result: ...)"。结果由引擎在两个厨房副本上算出来：一个副本把这个选项做到这一步结束（和选项联动表的做法一样），另一个副本里 Jeff 原地等同样长的时间，两边的另一位厨师都照常做手上的事；两边在那一刻的差别只写三类：这一步带来的钱（"serves O1 (Steak): +50"、没有订单要的菜、糊太久被拒收、丢弃食物、灶台着火），开始或停止加热的食物（"beef (cooked) heats again on Stove 2: it burns and Stove 2 catches fire in 1.4 s"），以及因为上面压着东西而拿不出、或重新能拿出食材的食材箱。等待时也会发生的事、之后的步骤都不写；一键选项放下手中物品的位置由 put_where 决定，那个位置上的结果也不写。`rules.effects` 说明这一点，并说明它不建议选哪个。决策循环在选项联动表的线程里计算它，研究回放从 `conditions.features` 读这个开关。每局的开局记录和研究记录都带上当时的开关（`features`：每个功能的 `on` 和 `version`）。游戏规则、关卡、玩家偏好和请求间隔这类数值仍在各自的文件里（`ai_ask_on_step_end` 暂时留在 `config.json`，因为搬走会改变每局的配置指纹）。

## 共用规则与扩展点

人类持续移动并执行就近动作，agent 选择较高层动作。双方共用移动速度、碰撞、操作侧、加工时间与物品约束。工作中的厨师不会被推离；锅仅在灶台上加热。

地图由 `map_definition.py` 校验。菜谱合法性与部分加工条件仍在 Python 中，路线图是先转为可校验数据，再接地图与菜谱编辑器。视觉配料叠层独立于合法性判断。

未来与社区共同定义完整对局 scenario schema、搭档／配置条件及对照方法。结果需记录输入语言和构建标识；消息或记忆送达可以直接观察，理解与因果适应需要相应对照。
